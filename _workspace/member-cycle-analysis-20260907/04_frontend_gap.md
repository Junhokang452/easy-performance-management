# 평가 프런트엔드 현황과 독립 화면 정보 구조 제안

- 작성일: 2026-09-07
- 범위: 현재 `frontend-vite`의 라우트·화면·공유 UI 사용 현황에 대한 읽기 전용 분석
- 제외: 코드 수정, API 변경, 서버 실행
- 원문 요구 근거: `01_primary_guides.md`, `02_supporting_guides.md`

## 1. 결론

현재 프런트는 평가 전 과정을 실제로 처리할 수 있지만, 거의 모든 역할과 단계를 `/` 및 `/workspace/:cycleId`의 한 세로형 워크스페이스에 모아 놓았다. 따라서 기능 수에 비해 사용자가 인식하는 화면 수와 탐색 깊이가 작다. 사이클 선택, 단계 표시, 운영 버튼, 참여자, 관리자 할 일, 보정, 결과, 피드백, 본인 평가가 같은 페이지에서 조건부 카드로 나타나므로 현재 단계에서 허용된 카드 몇 개만 보이는 순간 화면이 단순하게 느껴진다.

다음 개편은 이미 검증된 평가 기능을 **목록 → 사이클 상세 → 단계별 독립 작업 화면**으로 재배치하는 것에서 시작한다. 그러나 재배치만으로 원문 요구를 충족할 수는 없다. 현재 서버에는 평가별 선택 단계, 합의형/자기신고형 목표, 항목별 달성수준, 자기·1차·2차 등 다차수 평가, 항목별 점수·의견·필수 여부, 성과과제, 면담 기록의 공개 범위를 표현할 충분한 모델과 API가 없다. 부서 목표와 면담은 평가 사이클의 하위 카드가 아니라 별도 업무 영역으로 제공하고, 기존 `/workspace/:cycleId`는 요약 허브로 축소해야 한다.

### 1.1 원문 요구와 제품 확장 제안의 경계

| 구분 | 원문에서 확인된 요구 | 이 문서의 확장 제안 |
|---|---|---|
| 평가 단계 | 평가 설정에 따라 목표·중간점검·평가·조정·피드백 단계를 선택하거나 생략하고, 역할별로 수행한다. 자기·1차·2차 등의 차수 상태와 선후행이 존재한다. | 클릭 가능한 단계 내비게이션, route 메타데이터, “지금 할 일” 카드의 배치 방식 |
| 평가 항목 | 목표별 정의·가중치·달성수준, 항목별 등급/점수·의견, 의견 필수 여부, 차수별 의견을 보존한다. | 스냅샷 저장 방식과 화면 컴포넌트 분해 방식 |
| 성과과제 | 과제명·기간·단계·설명, 체크리스트/실적 방식, 목표 연결, 담당·관리·협업 관계자, 활동·파일·피드백·라벨을 관리한다. | 부서 실적 롤업, 여러 목표의 압축 입력, 자동 이상 탐지 |
| 면담 | 대상자·선택적 참조자, 요약·주요 이슈·요청·후속 조치 자유 서술, 대상자/참조자별 공개 옵션, 역할별 네 조회 탭이 필요하다. | 면담 일정, 사전 질문, 구조화된 후속 과제와 다음 면담 연결은 원문 미명시 제안 |
| 부서 목표 | 구성원은 소속 부서를 선택해 목표를 조회하며 수정하지 않는다. 개인 목표 작성 시 부서 목표를 선택·연결할 수 있다. | 부서 실적 롤업과 조직장·총감독·HR의 편집 권한은 원문에서 확정되지 않은 제안이며 관리자 가이드 확인 필요 |
| 이의·결과 | 구성원 이의 후 평가자가 재검토하고 추가 조정할 수 있다. | 재조정 결과를 새 버전으로 보존하고 재발행하는 구체적 상태·감사 모델은 관리자 가이드 확인 후 설계 |

따라서 이후 설계 문장에서 “필요하다”는 표현은 위 원문 요구를 뜻하고, route 이름·레이아웃·집계·일정·후속 과제 구조는 독자적인 제품 설계 제안으로 읽어야 한다.

## 2. 현재 프런트 구조

### 2.1 사용자가 실제로 보는 내비게이션

`App.tsx`에는 많은 lazy route가 선언돼 있지만, 왼쪽 내비게이션에는 다음 세 종류만 노출된다.

| 역할 | 노출 메뉴 | 근거 |
|---|---|---|
| 전 사용자 | 내 평가 또는 평가 운영 → `/` | `App.tsx:193` |
| HR_ADMIN, SUPER_ADMIN | 사이클 관리 → `/hr/cycles` | `App.tsx:194-201` |
| SUPER_ADMIN | 테넌트 관리 → `/admin/tenants` | `App.tsx:202-209` |

`/my/kpi`, `/kpi/alignment`, `/manager/review`, `/director/calibration`, `/hr/reports`, `/my/report`, `/personal-okrs`, `/mentor-feedbacks` 등의 route는 존재하지만 내비게이션에서 접근할 수 없다. 직접 URL을 아는 사용자에게만 보이는 사실상 숨은 화면이다.

또한 `ProtectedRoute`는 로그인 여부만 검사한다(`ProtectedRoute.tsx:14-21`). 화면 안에서 서버 권한과 `allowedActions`로 실제 작업을 제한하고 있으나, 프런트 route 자체에는 역할 메타데이터가 없다. 이 때문에 메뉴, route, 서버 권한을 한눈에 검토할 수 있는 단일 정보 구조가 없다.

### 2.2 평가 워크스페이스의 실제 구성

`EvaluationWorkspacePage`는 사이클, 현재 사용자, 통합 워크스페이스 응답을 한 번에 조회한 뒤 아래 패널을 한 페이지에 순서대로 배치한다(`EvaluationWorkspacePage.tsx:77-105`).

1. 사이클 전환 선택기
2. 읽기 전용 단계 레일
3. 다음 단계 진행을 막는 항목
4. HR 운영 버튼
5. 참여자·평가자 표
6. 관리자·총감독의 팀 평가 목록과 선택 상세
7. 보정 작업
8. 결과 분석
9. 피드백·이의 처리
10. 본인 목표, 실적, 중간점검, 자기평가, 결과

역할과 상태에 따라 일부 패널만 렌더링된다. 예를 들어 보정 패널은 보정 단계이면서 HR·총관리자·총감독일 때만 보이고, 팀 할 일은 매니저·총감독에게만 보인다. 이 방식은 허용되지 않은 가짜 버튼을 숨기고 실제 상태 전이를 지키는 데는 적합하지만, 각 업무의 독립된 장소와 맥락을 만들지 못한다.

현재 컴포넌트 크기도 한 화면 집중을 보여 준다.

| 파일 | 줄 수 | 한 파일에 포함된 책임 |
|---|---:|---|
| `MyEvaluationPanel.tsx` | 598 | 목표 작성·수정·승인 요청, 실적 기록과 이력, 중간점검, 자기평가, 결과, 확인, 피드백 수용·이의 |
| `TeamTasksPanel.tsx` | 366 | 팀 목록, 목표 승인, 중간점검 피드백, 관리자 점수 입력·제출 |
| `OperationsPanels.tsx` | 289 | 사이클 전이, 결과 발행·마감, 참여자 검색·배정·목록 |
| `FeedbackPanels.tsx` | 252 | 결과 분석, 관리자 피드백, HR 이의 처리 |
| `CalibrationPanel.tsx` | 195 | 세션 생성, 목표 분포, 등급 조정, 확정 |

### 2.3 기존 독립 화면의 상태

기존 페이지에는 KPI 트리, 목표 정렬, 자기평가, 관리자 평가, 보정 세션, 분포, 보고서 화면이 이미 있다. 다만 새 평가 워크스페이스와 병렬로 남아 있고 다음 문제가 있다.

- 사이클 관리 목록의 행은 편집·정책·상태 전이·삭제만 제공하고 사이클 상세로 들어가는 주 동작이 없다(`CyclesPage.tsx:124-145`, `CycleRow`).
- `/my/kpi`, `/my/self-review`, `/my/report`는 직원 UUID를 직접 입력해 로드하는 이전 관리형 흐름을 유지한다.
- KPI 트리와 보정 세션의 일부 폼도 조직·직원 UUID를 직접 받는다.
- 이전 페이지와 새 워크스페이스가 서로 다른 API 모듈과 상태 전이 표현을 사용하므로 사용자는 동일 업무의 두 표면을 만나게 된다.
- 개인 OKR, 회고 일지, 멘토 피드백 페이지는 별도 route로 존재하지만 평가 사이클·직원 바인딩·현재 할 일과 연결되지 않은 단순 목록 카드다.

이전 페이지의 시각 구성은 재사용할 수 있지만, 그대로 메뉴에 다시 노출하면 새 actor-bound 워크플로와 UUID 기반 이전 흐름이 충돌한다.

## 3. 화면이 단순하게 보이는 이유

### 3.1 한 route가 너무 많은 일을 한다

페이지가 업무별로 분리되지 않아 URL, 페이지 제목, 브라우저 이동 기록, 빵부스러기, 화면 단위 도움말이 모두 부족하다. 단계 레일은 현재 위치를 설명할 뿐 클릭 가능한 하위 내비게이션이 아니다. 사용자는 목표 작성에서 실적 기록으로 이동하는 경험 대신, 같은 카드가 상태에 따라 바뀌는 경험을 한다.

### 3.2 단계가 지나면 작업 맥락이 사라진다

`allowedActions`가 없는 폼은 렌더링하지 않는 올바른 정책을 사용하지만, 지나간 단계의 읽기 전용 요약이나 다음 단계 준비 화면도 함께 약해진다. 완료된 목표 합의, 중간점검 기록, 자기평가, 관리자 평가를 한 사이클 안에서 나란히 검토하기 어렵다.

단계 자체도 `ACTIVE → GOAL_SETTING → MID_REVIEW → SELF_REVIEW → MANAGER_REVIEW → CALIBRATION → FINALIZED`의 고정 맵이다. 원문처럼 평가 설정별 단계 생략, 합의형/자기신고형 분기, 자기·1차·2차 등의 동적 차수를 표현할 수 없다.

### 3.3 역할별 업무함과 상세가 한 카드에 붙어 있다

`TeamTasksPanel`은 평가 대상 목록과 선택한 사람의 모든 상세 작업을 같은 카드 아래에 이어 붙인다(`TeamTasksPanel.tsx:58-104`). 목록 필터, 마감일, 지연 상태, 일괄 진행도, 다음 대상 이동이 없다. 인원이 많아질수록 업무함으로서의 성격이 약해진다.

### 3.4 사이클 목록과 사이클 운영이 단절돼 있다

관리 목록에서 사이클 상세로 들어가는 명확한 링크가 없고, `/`은 자동으로 첫 사이클을 선택한다(`EvaluationWorkspacePage.tsx:29-31`). 최근 사이클, 진행 중 사이클, 종료된 사이클을 비교하고 의도적으로 선택하는 목록 경험이 부족하다.

### 3.5 부서 목표와 면담이 독립 업무로 모델링되지 않았다

KPI 트리·목표 정렬은 기술적으로 존재하지만 메뉴와 평가 사이클 작업에 연결되지 않는다. 면담은 `MentorFeedbackPage`의 단순 피드백 기록 수준이며, 원문이 요구하는 대상자·참조자, 기록별 공개 범위, 역할별 네 조회 탭을 표현하지 못한다. 일정·사전 질문·구조화된 후속 과제는 이를 보완하는 독자 확장 제안이며 원문 필수로 간주하지 않는다.

### 3.6 분석과 기록이 작업 폼 아래에 묻힌다

결과 지표, 분포, 실적 이력, 피드백은 개별 카드나 표로 구현돼 있으나 독립적인 개요·기록 화면으로 승격되지 않았다. 정보는 존재하지만 사용자가 탐색할 수 있는 제품 구조가 없다.

## 4. 제안 정보 구조

### 4.1 1차 내비게이션

제품 왼쪽 내비게이션을 역할별 업무 영역으로 구성한다. 메뉴 가시성은 프런트 역할과 서버가 내려 주는 접근 범위를 함께 사용하며, route 진입 시에도 역할 가드를 둔다.

| 영역 | 구성원 | 매니저 | 총감독 | HR 관리자 |
|---|---|---|---|---|
| 평가 | 내 평가 | 팀 평가 | 조직 평가 현황 | 평가 운영 |
| 목표 | 내 목표 | 목표 합의, 팀 목표 | 부서 목표 | 목표 정책·현황 |
| 실적·점검 | 내 실적, 중간점검 | 팀 점검 | 조직 진행 현황 | 진행 현황 |
| 평가 작성 | 자기평가 | 구성원 평가 | 조직 검토 | 제출 현황 |
| 보정 | 결과 보기 | 팀 결과 보기 | 보정 | 보정 운영 |
| 피드백·리포트 | 내 결과·피드백 | 피드백 업무함 | 결과 분석 | 발행·이의 처리 |
| 면담 | 내 면담 | 팀 면담 | 선택 노출 | 면담 현황 |
| 설정 | 없음 | 없음 | 없음 | 사이클·참여자·정책 |

모바일에서는 같은 구조를 서랍 메뉴로 유지하고, 현재 사이클 내부에서는 하단 또는 상단의 압축된 단계 내비게이션을 사용한다.

## 5. 화면별 설계

### 5.1 평가 목록 `/evaluations`

**목적:** 사용자가 자신에게 보이는 모든 사이클을 의도적으로 선택한다.

- 상단: 페이지 제목, 역할에 맞는 요약 지표, HR의 사이클 생성 버튼
- 필터: 진행 상태, 평가 기간, 내 할 일 유무, 조직 범위
- 목록 카드/표: 사이클명, 기간, 현재 단계, 내 진행률 또는 조직 진행률, 남은 할 일, 마감일, 다음 주 작업
- 기본 정렬: 진행 중 → 시작 예정 → 최근 종료
- 행 주 동작: `상세 보기`; 보조 동작은 역할과 `allowedActions`에 따라 표시
- 빈 상태: 구성원·매니저는 “배정된 평가 없음”, HR은 “첫 평가 만들기”

현재 scoped cycle API와 `CycleResponse`는 목록의 기반으로 활용할 수 있다. 다만 평가마다 활성 단계와 차수 구성이 달라지는 원문 요구를 반영하려면, 사이클 응답에 설정된 단계·차수·역할·기간을 제공하는 새 계약이 필요하다. 자동 첫 사이클 선택은 없애고 최근 선택은 URL 또는 사용자 환경설정으로 보존한다.

### 5.2 사이클 상세 `/evaluations/:cycleId`

**목적:** 해당 사이클의 상태와 다음 행동을 요약하는 허브다.

- 고정 컨텍스트 헤더: 사이클명, 기간, 상태, 역할, 이전/다음 사이클
- 클릭 가능한 단계 내비게이션: 접근 가능한 단계는 상세 화면으로 이동, 잠긴 단계는 이유 표시
- “지금 할 일” 카드: 서버 `allowedActions`와 blockers에서 가장 가까운 1~3개 행동만 표시
- 진행 개요: 목표 승인, 중간점검, 자기평가, 관리자 평가, 보정, 결과 확인 진행률
- 최근 활동: 목표 수정, 실적 추가, 피드백 완료 등의 시간순 기록
- 역할별 보조 영역: HR 운영 경고, 매니저 지연 대상, 구성원 다음 마감

현재 워크스페이스의 `PageHeader`, `CycleSwitcher`, `WorkflowPhaseRail`, `BlockerPanel`을 이 화면으로 이동하되, 작업 폼은 두지 않는다.

### 5.3 목표 수립·합의 `/evaluations/:cycleId/goals`

**구성원 화면**

- 목표 목록과 전체 가중치 합계
- 목표별 제목, 설명, 성공 기준, 목표값·단위, 가중치, 상태, 수정 요청 사유
- 초안 저장과 승인 요청을 분리
- 승인 후 읽기 전용 버전과 합의 이력 표시
- 부서 목표에서 연결된 상위 목표와 기여 관계 표시

**매니저 화면**

- 승인 대기 업무함과 직원별 상세를 master-detail로 분리
- 목표별 승인·수정 요청, 공통 검토 의견, 직원 간 가중치 이상 탐지
- 이전/다음 직원 이동과 처리 완료 후 자동 이동

현재 `GoalForm`, `GoalCard`, `useGoalDecisionMutation`, 목표 조회 훅은 기본 작성·합의 UI에 재사용한다. 그러나 현재의 제목·설명·가중치·목표값만으로는 원문의 항목 정의, 등급/점수 기준, 등급별 달성수준, 합의형/자기신고형 분기, 직무·공통 평가항목 선택, 목표 수정·합의 이력을 표현할 수 없다. 이 항목들은 새 백엔드 모델·스냅샷·API가 필요하다. `MyEvaluationPanel`과 `TeamTasksPanel`에서는 목표 책임을 분리한다.

### 5.4 성과과제 `/evaluations/:cycleId/tasks`와 실적 기록 `/evaluations/:cycleId/check-ins`

**성과과제 화면 — 원문 요구**

- 과제명, 기간, 단계, 설명, 달성 방식(체크리스트 또는 실적), 개인·부서 목표 연결
- 담당자·관리자·협업자 관계와 관계자 범위의 활동·파일·피드백 공유
- 속성·활동·피드백 탭, 라벨 생성·필터
- 계획 → 진행 중 → 완료/폐기의 보드형 상태 변경
- 체크리스트 방식의 진행률 자동 계산과 실적 방식의 진행률·진척 내용 직접 입력

현재 프런트와 서버에는 이 도메인이 없다. 기존 체크인 값을 과제처럼 표시해서는 안 되며, `PerformanceTask`, 관계자, 체크리스트, 활동, 첨부, 피드백, 라벨, 상태 이력을 위한 새 백엔드 계약과 ABAC가 필요하다. 진행률·활동은 평가 참고 근거이며 자동 평가 점수로 변환하지 않는다.

**실적 기록 화면**

- 승인 목표별 현재 실적, 목표 대비 달성률, 최근 업데이트
- 실적 기록 폼: 기준일, 실적값, 진행률, 설명, 근거 링크
- 타임라인: 실적 변경, 근거, 관리자 피드백을 날짜순으로 표시
- 여러 목표를 한 화면에서 빠르게 갱신하는 압축 입력 모드
- 지나간 기록은 읽기 전용이며 최신 기록을 명확히 표시
- 모바일은 목표 카드 안에 타임라인을 접고, 주 행동을 하단 고정 영역에 제공

현재 `CheckInForm`, `CheckInHistory`의 계약을 유지하되 별도 `GoalCheckInCard`와 `CheckInTimeline`으로 분리한다. 성과과제의 활동·체크리스트와 목표 실적 기록은 서로 연결할 수 있지만 같은 엔티티로 합치지 않는다.

### 5.5 중간점검 `/evaluations/:cycleId/mid-review`

**구성원:** 진행 상황, 성과, 장애물, 필요한 지원을 구조화해서 작성하고 매니저에게 제출한다. 목표·실적 요약을 같은 화면의 읽기 전용 문맥으로 제공한다.

**매니저:** 제출된 내용과 목표별 실적을 함께 보고 피드백을 저장한 뒤 완료한다. 저장과 완료의 차이를 명확히 표시하고, 완료 후 기록을 잠근다.

현재 네 개 입력 필드와 `PerformanceCommentPanel`을 재사용한다. 구성원 작성 화면과 매니저 검토 화면은 route 안에서 역할별 레이아웃으로 분리한다.

### 5.6 자기평가 `/evaluations/:cycleId/self-review`

- 승인 목표, 최종 실적, 자동 점수, 근거를 한 표에 제공
- 자기평가 의견과 다음 성장 계획 작성
- 제출 전 누락 항목 검사와 확인 대화상자
- 제출 후 전체 내용의 읽기 전용 스냅샷
- 이전 중간점검과 매니저 피드백 참조

현재의 단일 textarea는 원문 요구를 충족하지 못한다. 목표/평가항목별 등급 또는 점수, 항목별 의견과 필수 여부, 별도 종합 의견, 임시저장·완료 상태를 새 백엔드 계약으로 분리해야 한다. 구조화 값을 하나의 코멘트 문자열로 합치는 방식은 항목 수준 검증·이력·다차수 비교를 잃으므로 완성 목표에서는 사용하지 않는다.

### 5.7 구성원 평가 `/evaluations/:cycleId/team-reviews`

- 왼쪽/상단 업무함: 직원, 조직, 현재 상태, 제출 기한, 누락 점수, blockers
- 오른쪽/하단 상세: 목표·실적·자기평가 비교, KPI별 자동 점수와 관리자 점수, 종합 의견
- 필터: 미작성, 작성 중, 제출 완료, 지연
- 모든 항목 점수 입력 여부를 진행률로 표시
- 제출 후 읽기 전용 비교 화면

현재 `ManagerScoreForm`과 숨은 `ManagerReviewPage`의 비교·점수 UI를 합쳐 actor-bound API에 연결하고 UUID 기반 직원 선택을 제거한다. 동시에 자기·1차·2차 등 다차수, 차수별 평가자와 의견, 선후행, 이전 차수 공개 범위를 새 백엔드 모델로 표현해야 한다. 단일 `managerScore`와 단일 매니저 역할만으로는 원문 평가 작성 흐름을 완료할 수 없다.

### 5.8 보정 `/evaluations/:cycleId/calibration`

- 요약: 보정 가능 인원, 현재·목표 분포, 미제출/미확정 blockers
- 세션 목록: 상태, 범위, 참여자, 일정, 조정 수
- 보정 작업대: 직원·조직·원등급·조정등급·근거, 분포 변화 미리보기
- 확정: 영향을 받는 평가 수와 건너뛰는 평가를 확인한 뒤 실행
- 총감독은 조정 중심, HR은 세션·분포·확정 중심 레이아웃

현재 `CalibrationPanel`, `DirectorCalibrationPage`, `CalibrationAnalyticsPage`, `HrDistributionPage`의 시각 요소를 하나의 route 영역 아래 탭으로 재조합한다. 실제 지원되지 않는 등급 수정·이의 조정은 노출하지 않는다.

### 5.9 피드백·리포트

`/evaluations/:cycleId/results`

- 구성원: 최종 등급·점수, KPI 스냅샷, 매니저 의견, 분포, 결과 확인
- 매니저·총감독·HR: 조직/부서 결과 요약과 분포, 완료율

`/evaluations/:cycleId/feedback`

- 매니저: 결과 피드백 작성·완료 업무함
- 구성원: 피드백 수용 또는 이의 신청, 처리 상태와 기록
- HR·평가자: 이의 목록, 사유, 재검토, 추가 점수·등급 조정, 결과 재확정과 재발행
- 완료된 대화는 시간순 이력으로 표시

현재 `ResultPanel`, `ResultsAnalysisPanel`, `FeedbackOperationsPanel`, `HrReportsPage`, `MyReportPage`를 역할별 화면으로 분해한다. 현재 서버가 이의 해결에서 지원하는 것은 `UPHELD`뿐이라는 점은 현행 진단이다. 새 완성 목표에서는 원문에 명시된 평가자 재검토와 추가 조정을 관리자 가이드로 확인한 뒤, 조정 버전·재확정·재발행·감사 이력을 포함해야 한다. 보고서 발행과 재발행의 최종 권한은 관리자 가이드 확인 후 route 권한으로 고정한다.

### 5.10 부서 목표 `/department-goals`

평가 사이클 하위가 아닌 독립 메뉴로 제공하되 사이클 필터를 가진다.

- **원문 확인 범위:** 구성원이 왼쪽 조직도에서 소속 부서를 선택해 해당 부서 목표를 조회하고, 개인 목표 작성 때 설정에 따라 부서 목표를 선택·연결한다. 구성원은 부서 목표를 수정하지 않는다.
- **독자 확장 제안:** 회사 → 사업부 → 팀 → 개인의 목표 트리, 담당 조직, 가중치 완성도, 연결 직원 수, 실적 롤업, 사이클·BSC 관점·연결 여부 필터
- **관리자 가이드 확인 필요:** 부서 목표의 생성·수정 주체, 조직장·총감독·HR의 편집 권한, 상하위 조직 탐색 범위, 실적 롤업 계산
- 조직 ID는 `LookupSelect`로 선택하고 내부 UUID를 표시하지 않는다.

기존 `ManagerKpiTreePage`, `DirectorKpiTreePage`, `GoalAlignmentPage`, `KpiNodeTree`의 로직과 `PerformanceSelectableSurface`를 활용할 수 있다.

### 5.11 면담 `/interviews`

피드백 메모와 구분되는 독립 업무 흐름이 필요하다.

- **원문 확인 범위:** 대상자 검색, 선택적 참조자, 면담·코칭 요약, 주요 이슈, 요청, 후속 조치 자유 서술, 대상자/참조자별 공개 옵션, `내가 작성`·`나의 기록`·`직원별 기록`·`참조된 기록` 네 조회 탭, 목록 선택 후 오른쪽 상세
- **필수 권한 모델:** 작성자, 대상자, 참조자와 기록별 두 공개 플래그를 판정하는 ABAC. 단일 `public` 값이나 역할 하나로 축약할 수 없다.
- **독자 확장 제안:** 면담 일정, 예정/완료 상태, 사전 질문, 구조화된 후속 과제의 담당자·기한·완료 상태, 다음 면담 연결, 평가 사이클 문맥 요약
- **관리자 가이드 확인 필요:** 수정·삭제, 공개 철회, 관리자·감사자 예외 열람, 알림, 보존 기간

현재 `MentorFeedbackPage`와 `ReflectionJournalPage`의 카드 표현은 재사용 가능하지만, 원문 필수인 대상자·참조자·공개 범위·역할별 조회부터 새 도메인/API가 필요하다. 일정·사전 질문·구조화된 후속 과제는 그 위에 올리는 선택적 확장이다. API가 준비되기 전에는 빈 버튼이나 로컬 전용 저장을 만들지 않는다.

## 6. 컴포넌트와 데이터 경계

### 6.1 제품 내부에서 먼저 분리할 컴포넌트

```text
features/evaluations/
  routes/
    EvaluationListPage
    EvaluationOverviewPage
    GoalAgreementPage
    CheckInPage
    MidReviewPage
    SelfReviewPage
    TeamReviewQueuePage
    CalibrationWorkspacePage
    ResultsPage
    FeedbackPage
  components/
    CycleContextHeader
    EvaluationStageNavigation
    NextActionCard
    GoalEditor
    GoalSummaryCard
    GoalAgreementHistory
    CheckInEditor
    CheckInTimeline
    ReviewQueue
    ReviewSubjectHeader
    ReviewScoreEditor
    FeedbackTimeline
  queries/
    cycleQueries
    goalQueries
    reviewQueries
    calibrationQueries
    reportQueries
```

route 컴포넌트는 URL 파라미터와 역할·로딩·오류 경계를 담당하고, 편집 컴포넌트는 폼 상태만 담당한다. mutation 성공 후 무효화할 query key를 각 도메인 query 파일에 모은다. 서버의 `allowedActions`를 모든 쓰기 동작의 최종 기준으로 유지한다.

### 6.2 route 메타데이터

메뉴와 route를 별도로 하드코딩하지 않고 다음 속성을 가진 단일 route 정의에서 생성한다.

- path, label i18n key, icon
- 허용 역할 또는 서버 capability
- 사이클 컨텍스트 필요 여부
- 단계 접근 조건
- mobile 표시 방식
- breadcrumb 생성 함수

UI route guard는 사용성 경계이고, 서버 권한 검사를 대체하지 않는다.

### 6.3 화면 재배치와 별개로 필요한 신규 백엔드 경계

| 경계 | 현재 한계 | 새 계약에 필요한 핵심 |
|---|---|---|
| 평가 템플릿·단계 | 고정 cycle status 열거형 | 평가별 활성 단계, 단계 순서·생략, 기간, 역할, 완료 조건 |
| 목표 기준·합의 | 제목·설명·가중치·목표값과 단일 승인 상태 | 합의형/자기신고형, 항목 정의, 등급/점수 기준, 등급별 달성수준, 작성 의견, 수정·합의 이력, 기준 스냅샷 |
| 평가 항목·차수 | 자기 종합 의견 하나와 관리자 점수 하나 | 항목별 점수/등급·의견·필수 여부, 종합 의견, 자기·1차·2차/조정/최종 차수, 차수별 평가자·선후행·공개 범위 |
| 성과과제 | 도메인 없음 | 과제 속성, 달성 방식, 목표 연결, 관계자, 체크리스트, 실적, 활동·첨부·피드백, 라벨, 상태 이력, 관계자 ABAC |
| 면담 리뷰 | 일반 멘토 피드백 카드만 존재 | 작성자·대상자·참조자, 대상자 공개·참조자 공개 플래그, 네 조회 projection, 기록 내용, ABAC |
| 이의 이후 조정 | `UPHELD` 해결만 지원 | 평가자 재검토, 추가 조정, 결과 버전, 재확정·재발행, 이전 보고서 감사 이력 |

프런트 route 분리는 이 계약을 병렬 준비할 수 있지만, 위 기능을 기존 문자열 필드나 현재 check-in에 억지로 저장해서는 안 된다.

처음에는 performance 제품 내부 컴포넌트로 만들고, 최소 두 자매품에서 같은 상호작용이 확인된 뒤 `@easy/ui-components`로 승격한다.

## 9. 5개 언어 보존 기준

현재 ko/en/ja/zh-CN/vi 사전과 `I18nDict` 키 정합, `@easy/i18n-common` 공통 문구 연결을 유지한다.

- route 정의에는 표시 문자열 대신 i18n key만 저장한다.
- 상태명, 역할명, 단계명, 버튼, 빈 상태, 오류, 확인 대화상자를 모두 5개 사전에 추가한다.
- `{count}`, `{date}`, `{done}`, `{total}` 같은 placeholder를 언어별로 동일하게 유지한다.
- 직원명·조직명·사용자 입력은 번역하지 않는다.
- 영어 길이와 베트남어 길이를 기준으로 탭·버튼 줄바꿈을 검증한다.
- 중국어·일본어의 단어 경계와 한국어 조사 결합을 고려해 숫자 접미사를 문장형 메시지로 옮긴다.
- 공통 “저장/취소/로딩/데이터 없음”은 제품 사전에서 복제하지 않고 `@easy/i18n-common`을 사용한다.

## 10. 반응형·접근성 기준

- 390px에서 페이지 전체 가로 스크롤이 없어야 한다. 넓은 비교표만 내부 `UiTable.ScrollContainer`를 사용한다.
- 데스크톱 master-detail은 모바일에서 “목록 → 상세” 두 화면 또는 accordion으로 바뀐다.
- 열을 단순히 숨겨 의미를 잃지 말고 모바일 카드에 상태·다음 행동·마감 정보를 남긴다.
- 단계 레일은 색상 외에 완료/현재/예정/차단 텍스트를 제공한다.
- 버튼을 아이콘만으로 제공할 때 접근 가능한 이름을 둔다.
- 저장 중 중복 제출을 막고, 저장 성공·실패와 서버 blockers를 화면 안에서도 확인할 수 있게 한다.
- 포커스는 모달 종료 후 실행 버튼으로 돌아가고, 업무함 상세 전환 시 상세 제목으로 이동할 수 있어야 한다.

## 11. 권장 구현 순서

1. route 메타데이터와 역할별 내비게이션을 만들고 기존 워크스페이스를 사이클 상세 허브로 축소한다.
2. 평가 목록과 사이클 상세를 연결하고 사이클 행 전체에 상세 진입 동작을 제공한다.
3. 평가 템플릿의 동적 단계·차수와 목표 기준/합의 계약을 정의하고, 단계 레일을 서버 설정 기반으로 바꾼다.
4. `MyEvaluationPanel`을 목표, 실적, 중간점검, 자기평가, 결과 화면으로 분리하면서 항목 수준 계약으로 교체한다.
5. `TeamTasksPanel`을 목표 합의, 중간점검, 구성원 평가 업무함으로 분리하고 다차수 선후행을 적용한다.
6. 성과과제 도메인과 관계자 ABAC를 구현한 뒤 목표·중간점검·평가 근거에 연결한다.
7. 보정·결과·피드백의 기존 독립 페이지와 워크스페이스 패널을 하나의 actor-bound route 체계로 통합하고, 이의 이후 조정·재발행 버전을 추가한다.
8. 부서 목표를 기존 KPI 트리 기반의 독립 메뉴로 연결하고 UUID 입력을 조직 검색으로 교체한다. 실적 롤업과 편집 권한은 관리자 가이드 확인 후 별도 적용한다.
9. 면담의 원문 필수 기록·공개 ABAC를 먼저 구현하고, 일정·사전 질문·구조화된 후속 과제는 별도 확장으로 결정한다.
10. 기존 URL redirect와 숨은 이전 페이지 제거를 마지막에 수행한다.

각 단계에서 기존에 통과한 실제 평가 전체 흐름을 route가 달라진 상태로 다시 검증해야 한다. 핵심 시나리오는 사이클 생성·배정·오픈 → 목표 작성·승인 → 실적·중간점검 → 자기평가 → 구성원 평가 → 보정·발행 → 피드백 수용/이의 → 마감이며, 데스크톱과 390px 모바일을 모두 포함한다.

## 12. 구현 전 결정이 필요한 항목

- 구성원 평가 사이클 목록에 종료된 사이클을 몇 년까지 노출할지
- 단계가 끝난 뒤 이전 작성 내용을 어느 역할까지 읽을 수 있는지
- 자기평가의 구조화 필드를 서버에서 분리할지, 단일 코멘트 포맷으로 유지할지
- 부서 목표의 편집 권한 단위를 조직장, 총감독, HR 중 어디에 둘지
- 면담 기록의 비공개 메모, 공유 메모, HR 열람 권한
- 결과 이의가 받아들여졌을 때 등급 재조정·재발행 버전을 어떻게 남길지
- 과거 숨은 페이지의 기능 중 새 actor-bound 계약으로 아직 대체되지 않은 항목의 폐기 시점

목록과 사이클 상세의 탐색 구조는 먼저 분리할 수 있다. 그러나 목표 수립부터 평가·면담까지의 완성 목표는 동적 단계, 항목 수준 평가, 다차수, 성과과제, 면담 ABAC, 이의 이후 조정 버전의 서버 계약 없이는 달성할 수 없다. 화면만 옮긴 상태를 가이드 구현 완료로 판정하지 않는다.
